# Ordered room with durable file commits: the frozen contract (Fable seat)

Written before any expectation in this lab. The oracle in `oracle.mjs` checks exactly these statements. A change here needs a witness, written in this file, before a check changes.

Source: Astra's proposal sections 3 and 6 (`/Users/davidmiranda/big/20261112-sheet-impl/coedit-replan/astra-proposal.md`) and David's answers on forms 9 and 10 (`../../DECISIONS.md`).

## 1. Three states of an edit, two ledgers

- **Local.** The edit exists only in the tab that made it.
- **Shared.** A room admitted the edit into its one ordered history. Other tabs can see it. The lab records this in the **delivered ledger**.
- **Saved.** The host accepted a file write whose commit record covers the edit. The lab records this in the **saved ledger**.

The two ledgers are separate sets. Nothing moves an edit into the saved ledger except an accepted file write. Nothing removes an edit from the saved ledger: a room loss does not, and a restore does not (a restore adds a transition and a safety version, see section 5).

A tab shows three matching states for its own edits: pending, shared, saved.

## 2. What is promised

- **P1, saved is true.** When a tab shows an edit as saved, the edit is in the saved ledger.
- **P2, saved stays.** Every later file of the same document contains every saved edit, or a later recorded action that replaced it. The only exception is a version restore, and then the replaced file still exists as a version.
- **P3, shared survives a lost room while one holder stays open.** An edit that is shared but not saved survives the loss of its room as long as one tab that holds it stays open. "Survives" means it reaches a saved file through that tab. It may end in a recovery copy instead only in the two cases of section 6.
- **P4, a file is a prefix.** A fresh load of any accepted file equals the workbook after exactly the first `through` actions of its generation. It never contains part of a later action or a tab's pending edit.
- **P5, one order.** Every tab that has applied the same number of actions of a generation holds the same workbook. Delivery order on the network does not change the result.
- **P6, no silent drop.** Every edit of a tab that is still open ends in one of four states: saved, replaced by a later recorded action, refused with a notice that still holds the value (its row is gone), or kept in a recovery copy with a notice.

## 3. The witness: all tabs close, then the room is lost

Moves: one tab types into a cell, the room admits it, no save runs, the tab closes, the room is lost. After that no tab, no room and no file holds the edit. No protocol can bring it back.

So a room delivery cannot be the acknowledgement that promises survival. In this lab the delivered ledger holds the edit, the saved ledger never does, and no tab ever showed it as saved. Scenario `all-tabs-close-room-loss` runs these moves. The planted defect `ack-on-delivery` (show saved at delivery) makes P1 fail on the same moves.

The oracle takes an obligation off a shared edit only with this witness: at the moment the room was lost, or later before the edit was shared again, every tab that held it had closed. The oracle records the holder set.

## 4. Generations and the stale generation refusal

- A **generation** is one room instance and its one ordered history. A room is only ever created by an **establishing commit**: a conditional file write that leaves the tables unchanged and puts a new generation in the commit record. Two tabs that start a room at the same time both send one; the host's ETag check lets one win.
- The commit record lists, for each of the last `W` earlier generations, how many of its actions the file includes (`lineage`). The lab uses `W = 16`. It was 4 until the hardening pass; section 10 gives the reason.
- **Refusal rule.** A request, a receipt or an adopt offer that names a generation other than the room's own is refused before it enters the history. A save that was pinned to an older file is refused by the host's ETag check. A refused frame changes nothing. The tab that sent it follows section 6.
- A save whose answer never arrived is **unknown**. An unknown save clears no obligation and is never treated as saved or as failed. The tab reads the file: only the commit record in the file settles it.
- A tab never puts a newly fetched ETag on a snapshot it captured earlier. After a refusal it reads the file, learns from the record, and captures again.

## 5. Version restore

Sections 5 and 6 are the text frozen before the first run. The fuzzer then found cases this text got wrong. Section 9 lists every rule that changed, with the seed that forced it. Where section 9 and this text differ, section 9 is what the lab implements.

- The host first saves the room's complete current workbook (saved file plus every admitted action) as its own version, the **backup**. If a room is open and the backup cannot be written, the restore is refused.
- The host then writes the restored tables with a new generation, an empty `lineage`, and a `cut` entry that names the generation it replaced and how many of its actions the backup holds. The host restarts the room on that file.
- The replaced file stays in version history.
- A tab that was in the replaced generation:
  - drops shared edits that the backup holds;
  - writes a recovery copy of its complete workbook if it holds shared edits the backup does not hold (the room was already lost when the restore ran);
  - sends its own pending edits again. An edit that no longer fits (its row is not in the restored workbook) is kept in a recovery copy, and the tab shows a notice. No row is created for it.
- Shared edits from before the restore are never admitted into a generation after it.

## 6. After a room is lost

- A tab keeps its complete workbook, the ordered tail of actions the file does not yet cover (from every author), and its own pending requests.
- When the new generation's `lineage` names the tab's old generation, the tab offers its tail as **adopt** actions, in order. The room admits adopt action `n` of an old generation only when it has `n - 1`. So a tail goes in whole, from its start, and a cell never arrives ahead of its row. A second holder's copy is a duplicate and has no effect.
- The tab sends its own new edits only after its tail is in.
- A request carries a stable id (client, number). The committed workbook carries a small **request ledger**: for each client, the highest request number already resolved. A request at or below that number has no second effect. This settles a request that was in flight when the room was lost without comparing cell values.
- **Recovery copy instead of merge** in exactly two cases, never as a guess:
  1. the tab's old generation is not in `lineage` (more than `W` generations passed while it was away), or
  2. a restore cut it (section 5).
  In both cases the copy is a complete workbook written through the host's recovery path, and the tab shows a notice. A notice without stored bytes is not recovery.
- An ordinary session (every tab connected, one room loss) must end with every held edit saved in the document, with no recovery copy.

## 7. What the lab models and what it does not

- Workbook: one sheet, three fixed columns, rows with stable ids. Actions: set a cell, insert a row (the whole record), delete a row.
- Not modeled at the first freeze: formulas, undo, sort, move, columns and sheets as records, multipart pastes, file mode with no room, outside writes other than restore, the real ClayJS store, and any real host. Section 10 lists what the hardening pass added to the model. Still not modeled, so not proven here: formulas, undo, sort, move, columns and sheets as records, the real ClayJS store, and any real host.
- The host is a simulation: one file with an ETag, conditional writes, version history, a recovery store, and restore. A save answer can be accepted, refused, or lost (with the write applied or not applied).
- At the first freeze, reading the file and attaching to the room happened in one step. Since the hardening pass they are two steps that the fuzzer pulls apart (section 10, rule 18).

## 8. Witnesses for oracle changes

- **P6, a refusal that a later restore cut out of the history** (found by seed 47, ordered delivery, 300 moves, shrunk to 9 moves). Moves: tab 1 types `v2` into row 1; tab 2 deletes row 1 and the room admits the delete first; the room refuses tab 1's write because the row is gone, and tab 1 shows a refusal notice that holds `v2`; the room is lost; a restore to an earlier version brings row 1 back. The first oracle accepted a refusal only when the final file's history holds it. Here the history that held it was cut by the restore, so that rule reported a silent drop. It was not silent: P6 already lists "refused with a notice that still holds the value" as an end state. The oracle now accepts an edit that is outside the final history only when its own reference order refused it and the open tab shows a refusal notice that holds the same action. The check that the action was really refused comes from the oracle's reference fold, not from the tab.
- **P6, a row delete that the order refused** (found by seed 515, ordered delivery). Two tabs delete the same row. The room admits one delete. The second has no row to delete, so the order refuses it. The row is gone, which is what its author asked for. A later restore cut that history. The check for edits inside the final history never asked for a notice on a refused delete. The check for edits outside the final history did. Both now agree: a refused row delete or a repeated row insert needs no notice, because the workbook is already in the state the author asked for. A refused cell write still needs a notice that holds the value.
- **P3, who holds an edit** (found by the 100,000 seed sweep: seeds 76198, 82496 and 88955 with ordered delivery, seeds 25653, 29980, 36439, 75722 and 82026 with scrambled delivery; seed 88955 shrinks to 18 moves). Moves in seed 88955: a restore brings back a version with no row 4; tab 2 writes into row 4 from its older view; the room refuses the write because the row is gone; tab 4 receives that refused action; the room is lost; a second restore brings row 4 back; tab 2 sends the write again and the new room applies it; tab 2 closes; that room is lost before any tab received the applied action. The first oracle said a tab holds an edit when its tail has any action with that edit's id. Tab 4's tail has one, the refused one, so the oracle demanded that the edit be saved or copied. But tab 4 never had the value: a refused action changes no workbook, and a copy of tab 4's workbook could not hold it. No open tab ever held the applied edit, so this is the witness of section 3, not a P3 loss. The oracle now says a tab holds an edit only through an action that the oracle's own reference history applied in that action's generation, or through the author's own pending request. The reference decides, not the tab's flag. The planted defects that P3 catches (`recover-own-only`, `adopt-gap`) still fail after the change.
- **New checks, all added after a finding and all stricter.** R5: an edit that already settled never enters a room as a new request (seed 280; the check fails on the code before the fix). R6: an edit the replaced room or file already held never enters after the restore (seed 516, scrambled). G3: a room skips an adopt item only when the holder saw it as a duplicate (seed 1781). M1: the room's unsaved tail never passes its cap.

## 9. Rules that changed after the contract was frozen

Each rule below replaced or extended text in sections 5 and 6. The seed is the witness: it fails on the earlier rule and passes on this one. All seeds run at 400 moves and are replayed by `test/lab.test.mjs` from `regressions.json`.

1. **A restore folds the request ledger** (seed 516, scrambled). Section 5 said a tab "sends its own pending edits again". That let a request the replaced room had already admitted enter the new generation a second time, after edits that were built on it, so the final workbook showed an older value. Now the restored file's ledger takes, for each client, the higher of the restored version's number and the replaced room's number. The `cut` entry also carries both numbers for each client. A tab's request between the two numbers was in the replaced room: it is in the backup version, it is never sent again, and the tab shows a restore notice. Only requests above the higher number are sent again. One that no longer fits goes to a recovery copy.
2. **A tab trusts a file's ledger only with provable lineage** (seeds 516 and 347, scrambled). A tab learns which of its requests are resolved from a file only when that file's `lineage` or `cut` names the tab's generation. Otherwise it learns nothing from the file.
3. **A tab that lost held actions sends nothing again** (seed 347, scrambled). When a tab holds shared actions that neither the `lineage` nor a backup covers, its own pending edits may be built on them. It writes one recovery copy that holds everything unsaved, shows a notice, and reloads from the file. It does not replay any of its pending edits.
4. **Such a tab continues under a new client id** (seed 2577, scrambled). Another holder may still carry the tab's older requests in its tail. If the tab reused its request numbers, the room would take the older request for a duplicate of a new one.
5. **An adopt item for a duplicate carries no action** (seeds 3125 and 1781, ordered). When a held action was a duplicate at the holder, the offer carries only its position. The room advances the lineage count and applies nothing. An action the old room refused is offered with its action and judged again. This matters because ledger entries age out after `W` generations, so the new room cannot always recognize an old duplicate.
6. **The ledger and the cut age out.** An establishing commit drops ledger entries older than `W` generations. It drops the `cut` once the lineage holds `W` generations after the restore. A tab older than that is stranded and follows rule 3.
7. **A pending edit stays in the tab's view until the tab's own state covers it** (seed 223, ordered). Its status (pending, shared, saved, refused, recovered) is tracked separately. Removing it earlier made the tab's view step back for a moment.
8. **A tab that attaches posts a receipt when the file it read is ahead of the room** (seed 2527, ordered). Without it a room whose writer closed never learned that the save had landed.
9. **The room caps its unsaved tail, and a refused sender retries on progress** (seeds 48, 58, 435 and 1293, scrambled). The lab cap is 16 actions. A request or an adopt offer that would pass the cap is refused as full. The sender offers it again when a receipt or an adopt action arrives. A request that waits for an earlier one is woken whenever its client's ledger number advances, by a request or by an adopt action.
10. **Adopt offers travel in frames of two actions.** The gap rule in section 6 then meets real reordering under scrambled delivery. A holder offers again after the room's lineage count advances.
11. **Rotation.** A writer may start a new generation while the room is alive. The old room's tail is adopted the same way as after a loss. Scenario `rotation-carries-the-tail` and the fuzzer's `rotate` move cover it.
12. **Smaller corrections.** A second restore keeps a separate view for each restore's pending edits (seed 18). A lost answer to an establishing commit is resolved from the file by a tab that is already attached (seed 20). A tab captures its old view before it learns from the new file (seed 108). A shared edit that the new room refuses on adoption shows a refusal notice, not "saved" (seed 63). A lagging tab below the room's trim point reloads from the file and reports no progress when the file has moved to another generation (seed 518, scrambled).

## 10. Hardening pass

Every rule below was added or changed after both reviews (`review-astra.md`, `review-opus.md` in the run folder). Each has a witness: a scenario with a planted defect, or a seed, that fails without the rule. Where this section and sections 4 to 9 differ, this section is what the lab implements.

### Recovery copies

1. **A recovery copy stores the shared snapshot and the draft separately.** The `shared` document is the tab's applied state plus its held tail, with none of its own unsent edits. The `draft` document adds the tab's unsent edits, and is stored only when it differs. Witness: scenario `unsent-delete-keeps-shared-work` (Astra's `cross-recovery.mjs`), plants `copy-draft-only` and `copy-shared-only`.
2. **An edit that the tab cannot show is not listed as kept.** An unsent edit whose row is gone from the tab's own draft gets a refusal notice that holds the value (seed 5, scrambled, 7 moves; scenario `unsent-edit-with-no-row-left`, plant `homeless-silent`). A held shared paste that the tab cannot show whole, because one of its rows was deleted in the tab's current generation while other rows remain, is turned away the same way: a notice on the holder's tab carries the full action, and the copy does not list it (seed 285, scrambled, v3, 23 moves; scenario `held-paste-with-a-deleted-row`, plant `adrift-silent`).
3. **A held frame that the tab's current generation already resolved is not lost.** When a tab gives up, it skips a frame from an older generation whose request number its current generation's ledger already covers. The decision is in that generation's history. Witness: seed 285, ordered, v3, 21 moves; scenario `held-action-already-refused`, plant `lost-though-decided`. The same rule applies when a refused adopt offer strands a holder. Witness: seed 8515, scrambled, v3, 17 moves; plant `stranded-though-decided`.
4. **The oracle reads every recovery copy and every backup back from host storage**, with its own reader, when it is written and again at the end. It accepts a missing value in the shared part only when an action that its own reference applied replaces it. Witness: plants `recovery-empty-bytes` and `backup-empty-bytes`, and the storage test in `test/lab.test.mjs`.

5. **A snapshot does not apply an action twice.** A tab can hold the same action twice: the original in one generation, and the adopted copy in the next. When the lineage already covers the source position of a held adopted action, the snapshot skips it. Without the rule, a tab whose ledger no longer named the author applied the copy after a newer edit to the same cell, and the recovery copy showed the older value. Witness: seed 46843, ordered, v3, 44 moves; plant `snapshot-replays-adopted`. Three more cases of the same rule came from seeds beyond the gate, all in a tab that holds several generations of one client whose ledger entry is gone:
    - **The snapshot applies each held edit once, and skips only what the tab's own applied state resolves.** It used to skip by the running request count, so a paste that one generation had refused and the next had applied was skipped after a later request of the same client, while the copy still listed it. Witness: seed 818557, ordered, v3; plant `snapshot-skips-by-count`.
    - **An edit that is skipped because the file covers it stays skipped.** A later held copy of the same edit is not applied over newer work. Witness: 197 moves shrunk from seed 24945, scrambled, v3; plant `snapshot-forgets-covered`.
    - **A duplicate mark in a later held generation means the room has already decided the edit.** When a held generation skipped an adopted edit as a duplicate, and holds no earlier copy of it, a file in that generation's history had resolved the edit: applied it, or refused it. This is the same evidence as a ledger entry, for a client the ledger has dropped. So the snapshot does not apply an older held copy of the edit (witness: seed 24945, scrambled, v3, 2,000 moves; plant `snapshot-ignores-duplicates`), and the tab does not list the edit as lost when it gives up the older generation (witness: seed 518566, scrambled, v3; plant `listed-though-settled`). My first form of this rule did only the first half, and a holder then listed a refused paste in a copy that did not hold it. The second half then left one case open: the edit is the tab's own. A duplicate mark does not say whether the room applied the edit or refused it, so the tab does not show it as saved. It shows a refusal notice that holds the action, which is a final state and loses nothing (witness: seed 1649771, ordered, v3; plant `settled-own-left-open`). Without this the author's tab showed the edit as waiting for a save for good, though the file held it.

### Window and ledger

6. **`W = 16`.** Both reviews asked for it. The box sweep at 4, 8 and 16 is in `hardening-report.md`.
7. **The request ledger has a byte cap.** When the saved ledger passes 75% of the cap, the writer saves and then starts a new generation. An establishing commit over that mark drops the least recently active entries down to 50% and raises `floor` to the newest epoch it dropped. An outside write folds and trims the same way. The room refuses a request or an adopt item that would push the ledger past the cap, counted after the entry is written, for a known client as well as a new one (seed 253, v3: a known client's entry grew by one digit; scenario `known-client-at-the-ledger-cap`, plant `ledger-cap-new-clients-only`). Witness: scenario `thousand-clients-over-time`, plants `no-ledger-trim` and `no-ledger-cap`.
8. **A retired client is fenced.** A request carries the epoch its client id was made in. The room refuses a request from a client with no ledger entry that was made at or before `floor`, and an adopt item from a generation older than `floor` whose client has no entry. A tab that finds itself retired takes a new client id. It sends its unsent edits again only when none of them was ever sent. Otherwise it keeps them in a recovery copy with reason `retired`. A tab settles its own shared edits from lineage or cut coverage when its ledger entry is gone (seed 22, ordered, ledger cap 160). Witness: scenarios `retired-client-returns` and `holder-offers-a-retired-clients-action`, plant `retired-as-new`.
9. **Coverage is not acceptance.** A lineage entry advances when a holder carries an action into a later generation, and the room judges the action again at its new place. So when a tab's ledger entry is gone and the lineage covers its shared edit, the tab settles the edit by whether its rows still exist in the file: saved if they do, refused with a notice if they do not. This is the same test the tab uses when its ledger entry is present. Without the rule a tab showed a paste as saved though the room had refused it after a row delete. Witness: seeds 53457 and 57959, scrambled, v3; plant `coverage-means-saved`.
10. **A cut is not acceptance either.** After an outside write, the file's cut record tells a tab that the replaced room had resolved its request. It does not say whether the room applied the request or refused it. So the tab shows "kept in the backup version" only when it saw the edit applied in that generation. If its own view has no row for the edit, it shows a refusal notice that holds the action. If it cannot tell, the restore notice holds the action. Without the rule a paste that the room had refused after a row delete was shown as kept in a backup that did not hold it. Witness: seeds 271857 (ordered) and 95713 (scrambled), v3; scenario `refused-write-then-an-outside-write`; plant `cut-means-backed-up`.
11. **A tab reads again before it gives up its client id.** If the file a tab holds says its client was dropped, and that file is no longer the host's file, the tab reads the file again before it writes a recovery copy and takes a new id. Without the rule a tab wrote a recovery copy for an edit that a holder's save had just carried into the file. Witness: seed 29312, ordered, v3, 32 moves; plant `retire-on-stale-file`.

### Bytes and pastes

12. **Admission counts bytes against the real ClayJS caps.** The store is a fixed reserve for the commit record plus the bytes of the unsaved tail (4 MiB). The room also counts staged parts and parked requests (6 MiB). A frame holds at most 128 operations. An action has its own cap (3 MiB in the lab's reading). The lab runs at the real caps divided by 1,024, with 2 operations per frame, and one scenario runs at the real caps. A refused sender still retries on progress. Witness: scenarios `room-store-cap`, `staging-counts-against-the-room-cap`, `action-over-the-cap`, `twenty-thousand-cell-paste`; plants `no-tail-cap`, `no-stage-cap`, `no-action-cap`, `oversize-frame`.
13. **A paste is one action, applied all or nothing.** A paste over one frame's operations travels as part frames. The room stages them for that connection and admits one action when the last part arrives. A tab applies it only when every part has arrived. A holder offers a held paste in parts the same way. Witness: scenarios `paste-travels-in-parts` and `held-paste-is-recovered-whole`; plants `paste-part-admit`, `apply-partial-paste`.
14. **A frame that is next in order has first claim on room space.** The room drops parked requests and staged parts that are not next, and tells their senders to send again. It also drops a connection's staged parts and parked requests when the connection ends. Witness: seed 218, scrambled, v2, 69 moves (every tab waited for good).

### File body

15. **The file body is an HTML table with escaping**, taken from Astra's lab: `<tr data-id data-pos>`, `<td data-col>`, text escaped for `& < > "`, and the commit record in one JSON script tag with `<` written as `\u003c`. Stored versions and recovery copy parts use the same form. Witness: scenario `cell-text-is-escaped`, plant `no-escape`, and the codec test.

### The host boundary

16. **A room instance has an id, and the commit record names it.** The host creates an instance when a tab joins and no instance exists. An instance has no generation until it opens one. An establishing commit carries `room`, the id of the instance it was made for. An instance opens a generation only after it checks the host file: the record must name that generation and that instance. So a new instance after a restart or an expiry never continues the old instance's generation; the first tab starts a new one. A tab that reads a file naming the current instance asks the instance to open it. Witness: scenarios `empty-room-expires`, `restart-with-unsaved-work`, `stale-open-is-refused`; plants `open-unnamed`, `stale-open`; oracle rule H1.
17. **The host drops an empty room only when nothing is unsaved.** A room with unsaved actions stays until a tab returns or the server restarts. A restart is a room loss. Witness: scenario `last-tab-closes-and-the-room-stays`; plants `expire-dirty-room`, `attach-no-tail`; oracle rule H2.
18. **Reading the file and attaching are two steps.** A tab attaches only when the file it read is not older than the room's base. If it is older, the tab reads again. A tab that was touched between the two steps reads again. A tab does not save while it is between the two steps. Witness: scenario `stale-file-at-attach`, plant `attach-stale-file`; oracle rule P5 (a tab that has read the whole room stream is at the room's sequence).
19. **Every outside write goes through one host step.** A restore, an agent write and an upload of an older copy are the same step: back up a dirty room as a version, write the new tables with a new generation, an empty lineage and a cut, fold the ledger, and either reopen the room on the new generation or drop the room. An outside write that changes the tables and keeps the generation is a defect. Witness: scenarios `agent-write-through-the-host`, `upload-drops-the-room`; plant `outside-no-reset`; the per-step check that the host file is the last accepted commit and equals the reference.
20. **A tab does not repeat a refused write.** After the host refuses a conditional write, the tab reads the file before it writes again, and it never sends the refused ETag a second time. Witness: plant `412-no-fetch`; oracle rule L1.
21. **A room accepts a receipt only for its own generation and for a commit the host accepted.** Witness: plants `receipt-any-gen`, `receipt-before-accept`; oracle rules G1 and P1 at the receipt.
22. **File-only mode** (`fileonly.mjs`, a host with no room, such as HTML Clay). Each tab saves the whole file with a conditional write. The file carries the same request ledger. After a refused save the tab reads the file and puts only its unsaved edits on top. An outside write through the host keeps the ledger. A save that would pass the ledger's rotation mark trims the ledger and starts a new generation. Witness: scenarios `file-mode-*`; the thirteen `file-*` plants; oracle rules F1 to F9. The file-only fuzzer forced five rules:
    - **On every read the tab settles each pending request that the file's ledger covers**, not only on the first read after a lost answer. Witness: file-only seeds 1240 to 1613 of the first generator; scenario `file-mode-ledger-returns`, plant `file-settle-once`.
    - **A fold never brings back a client that the current ledger has dropped.** When the host writes an older version, an entry from that version is kept only if the current ledger still names the client or the entry's stamp is above the current floor. Witness: seed 14; scenario `file-mode-old-version-after-a-trim`, plant `file-fold-revives-retired`.
    - **An edit whose save once went unanswered is never sent under a new client id.** When a tab finds its client dropped, such an edit goes to a recovery copy. A tab does not change its client id while a save is in flight. Witness: seed 2734; scenario `file-mode-trimmed-version-returns`, plant `file-retired-resends`.
    - **A tab never saves in an epoch below one it has seen.** Another program can put back an older file. A tab that has seen a later epoch then starts a new generation above it when it saves. So the stamps of one client never go back, and the two stamp checks of the fold hold. Without the rule the epoch count ran a second time, a fold compared a stamp from the first run with a floor from the second, and a tab saved again what an outside write had cut out. Witness: seeds 592450 and 1607; scenario `file-mode-save-on-an-older-file-starts-a-new-epoch`, plant `file-save-reuses-epoch`. This rule replaces an earlier one (a tab lowers its birth epoch on a rollback), which it covers. The tab counts an epoch as seen from the moment it sends the save that starts it, because the answer can be lost. Witness: seed 1234348; plant `file-forgets-own-epoch`.
    - **A fold drops an entry that says less than the tables hold.** When only the replaced file names a client, and that entry's stamp is at or below the floor of the version the host writes, the version had dropped the client after later saves. The fold drops the entry. Witness: seed 599069 of the generator before the rule above; scenario `file-mode-old-entry-under-a-trimmed-version`, plant `file-fold-keeps-stale`.
    - An outside write moves the epoch above the folded floor, so a tab that opens after it is never taken for a dropped client.
23. **What file-only mode does not promise.** A raw overwrite by a program that does not know the protocol is modeled. After it a tab still never overwrites the other program's change (F2), and never saves again an edit it showed as saved (F9). But a raw copy of an older file also puts back an older ledger. So an edit whose save had no answer can be saved a second time on top of the older copy, and the oracle allows that after a raw overwrite (F4 is suspended for edits that were cut before it).

### Oracle changes

- **Holders by what a tab shows.** At a room loss a tab is a holder of a shared edit if its own records hold the action or if its view shows the value or a value built on it. Witness: scenario `a-tab-that-shows-a-value-holds-it`, plant `receipt-trims-all`. With the reading removed, the oracle raised nothing for that plant.
- **A second reading in the shared comparison** (`shared/holder.mjs`, Astra's holder and causal oracle): facts by value with their ancestor chain. It catches `resend-uncertain` in union recovery, which the id-based reading misses.
- **New rules, all stricter:** P7 (the room admitted an action that differs from the authored one), F1 (a frame over the operations cap reached the room), M1 in bytes, M2 to M4, H1, H2, L1, G1 and P1 at receipts, P5 for a tab at the end of the stream, and the per-step host file check.
- **One rule was made per tab instead of per edit.** `oracle.homeless` records which tab could not place an edit. The notice check for the author applies when the author is that tab. A holder that turns an edit away is taken off the obligation for that edit only after the oracle checks that an admitted delete removed one of its rows and that the notice carries the action.
- **One bound was loosened, on purpose.** The end-of-session loop gave up after 80 rounds. A tab with a long backlog saves one batch per round, so 11 honest seeds in 122,000 ran out of rounds while still saving (seed 23293, scrambled: 46 unsaved requests, all saved on one more call). The loop now gives up after 80 rounds with no accepted file write, with a hard limit of 3,200 rounds. The stall plants `unknown-never-resolved` and `no-idle-check` still fail with I8.
- **One end check was tightened.** A refused edit of an open tab now needs a notice that holds the action. A plain restore notice no longer passes (rule 10).
- **No other assertion was loosened or removed to get a green run.** In file-only mode, rule F4 was narrowed after a raw overwrite as rule 22 says, and rule F9 was added in the same step so that the opening covers only edits that were never shown as saved.

### Generator

Profile `v3` is the default. `v1` and `v2` stay so that old witness seeds replay under the moves they were found with. `v3` adds: `host` and `deliver` (a request lands in one move and its answer arrives in another, in any order, and either can be lost), `step` (read and attach apart), `expire`, `outside`, `lull` (the connected tabs wait until everything is saved), `leave` (a tab closes with a request in transit), `renew` (any attached tab starts a rotation), `text` and `clear`. Each seed draws traits: a weight factor per move, split linking, retained rooms, outside writes that reopen or drop the room, a ledger cap of 480, 160 or 120 bytes, one slow uplink and one slow downlink class, and a calm session in a quarter of the seeds. Only moves that do something count toward the move budget.

The file-only generator (`filefuzz.mjs`) draws its own traits: a weight factor per move, a ledger cap of 480, 160 or 102 bytes, lost answers at 5% to 50%, one sleepy tab, tabs that stay dark after a lost answer, and bursts of outside writes. An outside write takes the live file, one of the last four versions, any version, or the version that was live before the last outside write.

Both generators are frozen. The witness seeds in `regressions.json` depend on them. A new move table must be a new profile.

## 11. Fix round 1: recovery copies store held edits

David decided on form 12 that a recovery copy stores each held edit with its identity, source, order and room outcome (applied or refused), and leaves out edits already in the saved file. This section is what the lab implements for recovery copies. It replaces rules 1, 2, 4 and 5 under "Recovery copies" in section 10. The saved-file rules of sections 4 to 10 did not change: the room, the conditional file write, the ledger, the lineage, the cut record and the fences are the code that passed both reviews, and 400 sessions per delivery mode give the same counts of edits, accepted writes, generations, adoptions and restores on the old tree and the new one.

### The stored copy

24. **A copy is one stored page.** Its record holds `v: 3`, the copy id, the tab, the generation the tab gave up (`from`), the reason, the file the tab judged against (`onto`, and `tag` with the ETag in file-only mode), the base document of the table (`at`), and the list `edits`. Each stored edit holds: the edit id `e`; the client id `c`, request number `n` and the epoch the client id was made in `b`; the place a room admitted it, as the tab holds it (`src`, generation and sequence); the first place a room admitted it (`org`) and the places it was carried from (`via`); the outcome `out`; and the whole authored `action`.
25. **The outcome is what the tab can know.** `applied` or `refused`: what the room at `src` did with the edit. `unanswered`: the tab's own request, sent, and no room the tab can still see answered it. `unsent`: the tab's own request that never left the tab. `counted`: the tab's own request, parked across a restore, that the ledger of a file had counted when the tab read that file, and whose action does not fit that file. The tab cannot know whether a room applied it, so the entry does not say refused; it names the file in `file`. Witness: seeds 1351660 and 1009981 store the refused edit as refused; plant `copy-outcome-applied` fails with R3. Witness for `counted`: scenario `parked-request-the-file-counted`, and seeds 30137 (ordered) and 21677 (scrambled), where the room had applied the edit and another tab had then deleted its row; plant `counted-stored-as-refused` fails with R3. Seed 1244295 forced the split of `unanswered` from `unsent`: a request that a lost room had admitted must not be stored as never sent.
26. **The order is the order of the newest room.** Edits of the newest generation the tab holds come first, in that room's order, then older generations. An edit that the tab holds in several generations takes its place and outcome from the newest one. The tab's own edits that no room admitted come last, in the order the tab made them. Witness: scenario `copy-keeps-the-order-of-the-newest-room` and seed 101, ordered, v3; plant `copy-holder-order`. Two other orders were tried and failed: oldest generation first put an edit over one that was built on it, and first admission order broke the order of the newest room (both on seed 24945, scrambled, 2,000 moves).
27. **The table is only a preview.** It is the document at `at` with the stored edits on it that were not refused. Nothing reads the table to decide what a copy holds: the tab's notice lists the ids of the stored edits, read back from the stored bytes. Witness: scenario `lineage-beyond-window`, plant `copy-preview-stale`.
28. **A copy stores every held edit with its whole action.** This also holds for an edit whose row is gone and for a paste that the tab cannot show whole. Section 10 rule 2 gave those a notice only; the copy now holds the action, so nothing is listed that the bytes do not hold. Witness: scenarios `unsent-edit-with-no-row-left` (plant `copy-shared-only`), `unsent-delete-keeps-shared-work` (plants `copy-draft-only`, `copy-shared-only`) and `held-paste-with-a-deleted-row` (plant `copy-trims-paste`).
29. **Edits already in the saved file never enter a copy.** The tab leaves a held edit out when one of three things proves the file's history holds it: the lineage of the file covers a place where a room admitted the edit (`src`, `org` or one of `via`); the ledger of the tab's own generation had resolved the request (section 10 rule 3); or a later generation the tab holds skipped the edit as a duplicate (section 10 rule 5, third part). To make the first proof possible, room frames now carry `b`, `org` and `via`. No room rule reads them. A ledger number in a later file is not such a proof: after two restores in a row the count can stand for an edit that only a backup holds (seed 271857 failed P1 on my first form of the rule). The tab's own edit that is left out this way is settled at once: shown as saved, or as refused with a notice, by the same test as section 9 rule 9. This also holds when the tab gives up a lost generation while it follows a room, and the lineage that room started from covers the edit. Witness: seed 1609985, ordered, v3; plant `copy-keeps-saved` fails with R7. Witness for the settle: seed 145936, ordered, v3; plant `saved-own-left-shared` fails with P6 (the edit stays shared to the end).
30. **The tab reads the stored bytes back before it reports.** It writes the copy, reads it from the host, and compares. Only then does it show the notice and mark its own edits as recovered. If the bytes differ or are missing, it keeps the copy and writes it again on its next read of the file. Witness: scenarios `copy-write-the-host-dropped` and `copy-write-the-host-blanked`, plant `recovery-unconfirmed`; plants `recovery-no-bytes` and `recovery-empty-bytes` on `lineage-beyond-window`. While a copy is not stored, its edits are not open requests: the tab does not send them, park them or put them in a second copy. Witness: seed 670, scrambled, v4 (the session did not end); plant `unstored-edit-stays-open`.

### What the oracle checks on a stored copy

The oracle reads the stored page with its own reader (`reader.mjs`), when the tab reports the copy and again at the end.

- **R4.** The host holds the copy that a notice names.
- **R3, each stored edit against what was authored and admitted.** The action equals the authored action. Every place in `src`, `org` and `via` is a place where the reference room admitted that edit. The outcome equals what the reference did at `src`. An edit stored as never sent was never admitted. An edit stored as counted names a file the host accepted, the history of that file holds the edit, and the action does not fit that file. No edit is stored as refused without a place. Edits of one generation are in sequence order, a newer generation comes before an older one, and edits no room admitted come last. Every id a notice lists is stored. The table equals the reference document at `at` with the stored edits on it.
- **R7, saved edits stay out.** No stored edit that was not refused has a place that the lineage of `onto` covers. No stored edit comes from another generation when the tab's own generation had resolved the request, or when a later generation the tab holds had skipped it.
- **R2.** As before: a tab writes no copy for a generation that is in the lineage of the file. The oracle reads the header from the stored bytes and judges it against the file and the room as they were when the tab built the copy. The replay onto `onto` at report time also uses the set of replaced edits of that moment. A tab whose first write the host dropped reports the copy later, and by then other tabs may have saved or replaced the same edits; the earlier form judged with the later state. Witness: seeds 9958 (scrambled) and 65549 (ordered), profile v4: 111 of 250,000 v4 sessions failed the earlier form, each one with a host fault.
- **Counted, not failed:** `unprovable`, the stored edits that the history of `onto` holds and that no lineage, own ledger or duplicate mark could prove to the tab. They exist because the evidence is bounded (window of 16, ledger cap). Rule 31 keeps them from being written twice.

### Restore from a copy (replaces the old R3)

The old R3 looked for the edit's cells in the copy's table and could not fail when a later action had written the same cell. The new check replays the stored edits.

31. **A restore from a copy goes through the ledger check.** `recover.mjs` takes a file and a stored copy and decides each stored edit in order, by the checks a room makes on a request that arrives late:
    - `refused`: the room refused it. It is never applied, and it leaves no mark in the file. Inside one restore it lets the same client's next request follow, as it did in that room: the count moves over the refused request only when the restore takes that later request.
    - `saved`: the file's lineage covers a place where a room admitted it. `resolved`: the file's ledger counts the request. `replaced`: the cut record names a place where a room admitted it. None is applied.
    - An edit stored as `counted` is never applied: it is reported as `resolved` when the file's ledger still counts it, and as `unjudged` when it does not.
    - `new`: applied, or `misfit` when its rows are gone. An edit is new only when two things hold. First, no fold can have dropped the client's count: the epoch of `org` (or `b` for a request that no room answered or that never left the tab) is above the file's `floor` and inside the window. Second, the client's count stands at the request before this one, which is the rule a room applies to a request. This holds for an edit that never left its tab too.
    - `unjudged`: none of the above. The edit stays in the copy for a person to decide.
    - A restore counts each request it takes in the file's ledger, as a room does. That count is the only mark it leaves. A second restore from the same copy, or from another copy that holds the same edit, finds the request counted and takes nothing twice. There is no ledger entry for the copy itself.
32. **The oracle replays every copy four times:** onto `onto` when the copy is reported, onto the final file at the end, and at the end all copies one after another onto the final file, once in the order they were made and once in the opposite order. The two orders matter: with `replay-counts-a-refusal` planted, seed 36439 (scrambled, v1) passes in the first order and fails in the second, and with `replay-over-a-gap` planted so does seed 515 (ordered, v1). Other orders of three or more copies are not tried. It fails when a replay takes as new an edit that the file's history holds, or that a restore replaced (it is in a cut version or a backup); when it writes an edit over a value that was built on it (Opus's example); when it skips as already in the file an edit that no history, cut version or backup holds; and when a second replay takes anything. One skip of the third kind is right and passes: an earlier restore in the row took a later request of the same client after a room's refusal of the edit, so the edit can no longer be applied in order.
    - Witnesses: `restore-skips-ledger` (18 scenarios, among them `retired-client-returns`, `holder-offers-a-retired-clients-action` and `file-mode-saved-edit-with-a-lost-answer`, and seed 1244295). `replay-forgets-itself`, a restore that does not count what it takes (scenario `copy-keeps-the-order-of-the-newest-room`; seed 24945, scrambled, 2,000 moves). `replay-over-a-gap` (seeds 299 and 576, ordered, v3). `replay-trusts-a-returned-count` (seed 664, ordered, v3: a restore's fold dropped a client's ledger entry, a later restore of an older version brought it back with a lower count, and my first form of the check took as new an edit that the first restore had replaced). `copy-holder-order` (rule 26).
    - An edit that never left its tab is not exempt from the order. Witness: seeds 9656 (ordered) and 15983 (scrambled), found by the first box gate of this round in 14 of 375,000 sessions. My first form took such an edit as new with no check, because no file can hold it. On seed 9656 a restore from the author's copy took `t1:6`, `t1:7` and `t1:8` while `t1:3` to `t1:5` were not resolved; a restore from a holder's copy then took `t1:3` and put its older value over the value of `t1:8`. Plant `replay-unsent-out-of-order` (also caught by scenario `unsent-delete-keeps-shared-work`).
    - A refusal by a lost room is not a fact about the file. Witness: seed 818557, ordered, v3. One tab's copy stores `t3:1` as refused by generation 8, and two other copies store it as applied by generation 9, which adopted it later. My first form counted the refused request in the file's ledger. Then the order of two restores decided whether the edit of generation 9 was taken, and the oracle had to excuse every skip after a stored refusal. Now the refusal stays out of the ledger, and in either order the edit is taken from a copy that stores the outcome of generation 9 (on this seed its row is gone from the final file, so it is reported as a misfit). Plant `replay-counts-a-refusal`.
    - The lab does not run a restore from a copy as a move of a live room. It is a judgment on a file and a copy, and the oracle checks its decisions. The restore needs nothing in the file that the room does not already keep.
    - The price of the strict order, measured on 400 ordered sessions (seeds 1 to 400, 16,277 stored edits). A restore of every copy onto the final file applies 3,939 edits, finds 692 that no longer fit, skips 487 as already in the file, never applies 679 that are stored as refused, and leaves 10,480 for a person, because by the end most counts are outside the window or below the floor. Right after a copy is written the share is higher: over all replays onto the file a copy was judged against (a copy that is written again is replayed again), 9,873 decisions were applied and 4,159 were left for a person. My first form, which took never-sent edits with no check, applied 7,052 at the end; that form is the one seed 9656 broke.

### The end check for a refused edit that a lost room applied (P6)

33. **Scoped as both reviewers set it.** `oracle.refused` is unchanged: a later applied admission still clears it. `oracle.everRefused` is new and sticky: the first place the reference refused the edit. At the one place where the end check failed with "no saved file, no recovery copy and no refusal", it now passes only when all three hold: the reference refused the edit at some time; the author's refusal notice holds the exact action; the author's tab shows the edit as dropped. A refused edit that a tab's own copy stores as refused does not count as recovered for this check. Witness: seeds 1009981 and 1351660, ordered, v3; plant `refusal-notice-no-action` fails with P6. Astra's controls are a test: without the notice, with a wrong action in the notice, and with the sticky record removed, the end check fails with P6; with the tab showing the edit as saved it fails with P1; with a live holder, P3; with a lost saved edit, P2.

### File-only mode

34. **The same copy format.** A file-only copy stores each edit whose save got no answer: the action, the client id and request number it was last sent under, and `sent`, the commit of the save that carried it and whether the tab had judged it to fit. There is no room, so the outcome is always `unanswered`. The table is the file the tab read with the stored edits on it. The tab reads the stored bytes back before it reports, and sends no save while a copy is not stored. Witness: `file-copy-unconfirmed` (two scenarios with a host fault).
35. **A tab never shows a value as recovered unless stored bytes hold it** (Astra's case). The stored edit holds the action even when its row is gone from the file. The oracle checks each stored edit against the authored action when the copy is reported, and at the end reads the copy again for every edit a tab shows as recovered. Witness: scenario `file-mode-refused-edit-with-a-lost-answer`, plant `file-copy-table-only`; Astra's four cases are a test.
36. **Saved edits stay out.** A copy is made only when the file has dropped the tab's client, so the ledger cannot say whether the save landed. If the ledger still counts the client, the tab settles the edit from the count. Witness: plant `file-copy-keeps-saved` on `file-mode-lost-answer` fails with R7. An edit whose save did land and whose client was then dropped is in the file and in a copy; a restore from that copy does not apply it, because the ledger cannot judge it (scenario `file-mode-saved-edit-with-a-lost-answer`, plant `restore-skips-ledger`).
37. **A pushed document goes through the read path.** HTML Clay relays every saved document, with its ETag, to the other open tabs, in order per tab, and pushes an outside change of the file too (`htmlclay/internal/server/livesync.go`, `relay` and `publishExternalChange`). In the lab the host queues the stored bytes and the ETag for every other open tab after an accepted save, and for every open tab after an outside write. A `push` move delivers the oldest queued push of one tab, or loses it. The tab runs one function for a read and for a push: it marks requests with a lost answer, reads the ledger, settles, and takes the document as its new base under its unsaved edits.
    - Witness: `file-push-skips-rebase` (the tab takes only the ETag: F2, another tab's saved edit is overwritten; scenario `file-mode-push-while-editing`). `file-push-skips-settle` (the tab takes the document and does not read the ledger: under the fuzzer an edit is saved twice, F3 or F4; scenario `file-mode-push-after-a-lost-answer` fails on its own expectation).
    - **A tab never gives up its client on a pushed document.** A push can be older than the file the tab has read, so "the ledger has no entry for me and its floor has passed my client" can be false for the file. On that finding the tab reads the file and decides there. The oracle fails a copy that was made from a file the host had already replaced. Witness: scenario `file-mode-old-push-after-a-raw-replace`, plant `file-push-retires`.

- `snapshot-replays-adopted`, `snapshot-skips-by-count`, `snapshot-forgets-covered`, `snapshot-ignores-duplicates`: each was a defect in how a tab folded its held actions into the copy's table (section 10 rule 5). A copy no longer stores a folded table that anything relies on, so the code these defects changed is gone. Their seeds (46843, 818557, 24945 and its shrunk move list) stay in `regressions.json` as plain seeds.
- `homeless-silent`, `adrift-silent`: each listed in a copy an edit that the copy's tables could not hold. A copy now holds the action itself (rule 28).
- `cut-means-backed-up` stays. Its two seeds (271857, 95713) now keep the edit in a recovery copy, so the defect has a directed scenario instead: `cut-request-the-room-refused`.

### Generators

## 12. Fix round 2: write-once copies, the conflict rule, and restore in the room

Both reviews of fix round 1 named the same gaps in recovery copies. This section is what the lab implements for them. The saved-file rules of sections 4 to 10 did not change: with the old frame cost switched on (`LAB_FRAME_COST=action`) the counts of saved edits, accepted writes, losses, generations, adoptions, restores and renewals are equal to the tree before this round. The copy format is now version 4 (`saw` on every stored edit, `refused` on the record).

### Storing a copy

38. **A tab does not settle an edit that waits in a copy the host has not stored** (Opus finding 1). Story: a person's copy write fails, their tab reads the next file, and the tab shows the edit as saved when only a backup version holds it. `learnFromFile` skips such an edit until the copy's bytes are confirmed. Witness: planted defect `unstored-edit-settles` (10 moves shrunk from seed 1121, profile `v5`; 20 of 600 sessions at fault rate 0.5).
39. **A fault can hit any write of a copy, a retry included.** The host model takes a fault rate and a longest run of failed writes in a row. Four kinds: the write is dropped, stored blank, stored cut in half, or stored whole while the read back fails. `fuzz.mjs --faults rate[:run]` sets the rate for any profile, up to 1. Room profile `v5` and file-only profile `v3` draw a rate of 0.1, 0.3, 0.6 or 1 for a session. Profiles `v1` to `v4` and file-only `v1`, `v2` are unchanged.
40. **A copy is written once** (Opus finding 2). Story: a failed second write of a copy erases edits that a notice already lists as recovered. A copy whose bytes a tab has confirmed is never written again. Each later batch of edits that a restore left without a place gets a new copy id, as file-only mode already did. The oracle fails any write to a confirmed copy id (R4). Witness: planted defect `copy-written-again` (the old code that added to a copy and wrote it again; 6 moves shrunk from seed 7).

### The conflict rule (for David's approval)

The whole rule is in `conflict.mjs`: what an author saw (`seenBy`), whether an edit's rows still exist (`fitsNow`), and which cells no longer hold the seen value (`conflicts`). `recover.mjs` calls it from one function, `weigh`, which the pure restore and the room both use.

41. **Each edit records the value its author saw in each cell it writes** (`saw`). The value is what the author's tab showed when the edit was made, with the tab's own unsent and held edits. A cell edit and a paste record one value per cell. A row delete records the filled cells of the row. A row insert records nothing. The values travel in the request, in the room's action frame, in adopt offers, in the parts of a big paste, and in every stored edit. The oracle checks them at every admission and in every stored copy against what the author's tab showed. Witness: planted defect `saw-from-shared`.
42. **A restore writes a cell only if the cell still holds that value** (Astra finding 1, Opus finding 3). Story: a coworker saves a newer value in a cell, and a restore from an old copy puts the old value back with no notice. An edit that the ledger check takes as new and whose rows exist is applied only if every cell it writes still holds the value its author saw. Otherwise the decision is `conflict`, with the current value next to the copy's value for each cell that changed. A row delete is a conflict if any cell of the row changed. Witnesses: planted defect `restore-ignores-seen`, scenarios `room-restore-after-a-coworker-edit` and `restore-judges-a-paste-as-a-whole`.
43. **A paste is judged as a whole.** If any cell conflicts, no cell is written. Witness: planted defect `conflict-per-cell`.
44. **A conflict writes nothing and is not counted in the ledger.** So every later restore finds the same conflict until a person decides. The price: the same author's later edits in that copy are left for a person too (`behind` in the counts), because the ledger holds one count per client and a later request cannot be counted before an earlier one. An edit whose rows are gone is still reported as `misfit` and counted, as in round 1, unless an earlier insert of the same copy that creates its row still waits (rule 56, fix round 3).
45. **A second replay may take an edit that the first left behind a conflict,** when the first replay's own later writes put the seen value back into the cell. The oracle allows a second take only for a client that had a conflict in the first replay, and counts it (`again`).

### What the oracle checks on a restore

46. **The oracle folds the claimed decisions into its own document and ledger** (Astra finding 2, Opus finding 4), with its own reference step, and compares both with the document and ledger the restore returns. It also checks that the lineage, the cut record, the floor and the commit record are unchanged, and that each taken request was its client's next. Class R8 is new: a restore wrote over a value the author did not see, reported a conflict that is not one, or reported the wrong cells. Witnesses: planted defects `restore-half-paste` (Opus), `restore-reports-applied` and `restore-touches-another-cell` (Astra).
47. **The oracle checks stored client identity against its own evidence** (Astra finding 3). It records each edit's client, request number and birth epoch when the edit is made and when a tab renumbers its open requests, checks every request on the wire against that, and records the identity the room admitted at each place. A stored edit with a room place must match the room's record. A stored edit with no place must match the author's record, and "never sent" must be true. Witnesses: planted defects `copy-wrong-client` (Astra) and `copy-born-now`.
48. **P2 runs before the end check skips an edit that a copy stores.** A saved edit that the final history lost fails, also when a copy holds it. Witness: a control in `test/lab.test.mjs`.

### Frames

49. **The frame byte model counts what a frame carries** (Opus finding 5): the action, the seen values, the birth epoch, the origin and the path, plus 64 bytes. The room checks its caps with that cost, and the oracle computes it on its own. A 20,000-cell paste costs about 784 KB in the room store, up from 575 KB, because of the seen values. Witness: planted defect `frame-cost-action-only`, scenario `twenty-thousand-cell-paste`.
50. **Action and adopt frames no longer carry the birth epoch** (Astra's simplification). A request and a stored own edit keep it. The oracle fails a broadcast frame that carries it. Witness: planted defect `broadcast-carries-birth`. `replay-trusts-a-returned-count` still fails on seed 664.

### Restore in the room

51. **A restore from a copy is a move in the room.** A tab reads a stored copy and offers its edits to the room one at a time, in the copy's order (`copy` frames, split into parts like a request when a paste is big). The room judges each offered edit with `weigh`, the same function as the pure restore, against its own ledger and document. It appends a taken edit as a normal action frame that names the copy and keeps the edit's client, request number, origin and path. Every tab applies that frame, and the normal conditional write saves it. For the other decisions the room appends nothing and answers the tab. Witness: scenario `room-restore-applies-and-saves`; planted defect `room-restore-trusts-the-tab`.
52. **Exactly once is the ledger's job.** A stored edit that a room took is counted, so a second restore, the author's own resend and a holder's adopt offer all find it counted. Witnesses: scenarios `two-tabs-restore-the-same-copy`, `room-restore-before-a-coworker-edit` (planted defect `restore-skips-ledger`).

### The dependency hold (for David's approval, with the conflict rule)

### Notice outcomes

### A person's decision on a conflict

67. **A decision is a restore job on the same copy.** A tab that shows a restore notice with conflicts starts a new job on that copy and offers every stored edit again, in the copy's order. The frames of the decided edits carry the choice. The room judges every frame with `weigh`, as in any restore, so a decision goes through the ledger, the dependency hold and the rule that the tab reports after the save. The oracle records each choice when the tab makes it, from the conflict its notice shows.
68. **"Keep the current value" is a counted frame that writes nothing.** The room appends an action frame with the mark `keep`, the reducer counts the request and does not act, and every tab does the same. If the edit's rows are gone by then, the room counts it as refused, as for any stored edit. A tab that holds a keep frame of a lost room offers it to the next room with the mark (class G3). Witnesses: planted defects `decision-keep-not-counted` and `adopt-drops-keep`, scenarios `room-restore-holds-then-a-keep-releases` and `decision-across-a-room-loss`.

A paste is still judged as a whole. Reading note: the brief says "the value the author saw", and a conflict means the cell no longer holds that, so the lab compares with what the person reviewed, as Astra's condition says. Witnesses: planted defect `decision-take-unchecked`, scenarios `decision-take-writes-the-copy-value` and `decision-take-races-a-live-edit`.

A decision that a room counted and lost before a save comes back through a tab that holds its frame. A decision that no room has answered stays with its job, which offers the copy again in the next room. If the deciding tab closes first, the decision is gone, and the copy shows the conflict to the next restore. Witnesses: planted defect `decision-applies-twice`, scenarios `two-tabs-decide-on-the-same-conflict` and `decision-with-a-lost-save-answer`.

### The decision record (new, for David)

82. **A write-once record of marks next to the copies.** The host keeps a list of marks `{copy, e, kind}` (`host.decisions`, `keepDecision`, `fetchDecision`). `open`: a restore passed over a conflict or a held edit, and no person has decided it. `refused`: a restore passed over a stored refusal whose rows are back. Closing marks: `taken` (a person's take is saved), `saved` (the sheet holds the value), `kept` (a person kept the current value), `misfit` (no place left for it). A mark is never changed or removed, so two tabs cannot erase each other's marks. An edit's verdict is its closing mark if it has one, else `open` or `refused`. Marks are looked up by edit id across copies, because two holders can store the same edit in two copies. A mark write can fail like a copy write (same fault model, a lost answer included), and the tab retries it. A closing mark is permanent: neither a file position nor the author's ledger entry can show later that a close still holds after a version restore, so an edit that the ledger counts and the record closes is never judged late again; it reads "counted, not in the sheet" unless the sheet holds its value. An edit that the ledger does not count is judged as any stored edit is, also when the record closes it (after a version restore brought its rows back, for example); a pass over it writes no new mark, because marks are write-once and a closing mark wins. An `open` mark is always safe: a wrong one turns "counted" into "ask a person", never into a write.
83. **The mark comes before the pass can bury the edit.** A tab writes the `open` or `refused` mark of an answer and has it confirmed before it offers the next stored edit of the job, so the ledger never counts a passed edit that the record does not list. A tab with marks still to write is not idle. Story: Dana's restore passes over Sam's A1 and applies his B1; if B1 were counted before A1's mark is on the host and Dana's tab closed, every later restore would read A1 as "counted, not in the sheet", and nothing would ask anybody to decide it. Witnesses: planted defect `pass-without-record`, scenario `passed-conflict-stays-open-after-its-restorer-leaves`.
84. **A later restore judges an open edit again, without the ledger.** The tab names an offered edit `open` when the record lists it so. The room then does not answer "counted": it judges the edit as if the ledger did not count it, and the answer carries `late`. Held behind an earlier waiting edit (`held`). The sheet holds its value (`resolved` with the value shown; the job closes the mark as `saved`). Its rows are gone (`misfit`, closed as such). A person's keep (`kept`, closed as such). A person's take whose reviewed values still stand (`take`, rule 85). Otherwise a conflict line with the current value next to the stored one. A restore never writes a late edit by itself: the author's own tab may have written it after the mark was made, so only a person's take writes it. The room answers by the ledger as in round 3 when its own history holds a frame for that edit (a decision frame, an adopted frame, the author's own request) or a late keep it answered (`room.settled`), so two tabs that decide differently on a conflict that the ledger did not count yet still get round 3's answer: the first decision to reach the room wins. Witnesses: planted defect `restore-ignores-record`, scenarios `passed-conflict-stays-open-after-its-restorer-leaves` (Sam, Tom and Dana; Dana closes her tab, a second restore and Sam's tab both still see the open conflict) and `room-restore-passes-a-conflict-across-a-room-loss`.

For a passed edit: "keep" writes no frame, and the job closes the mark as `kept`; a keep that the room finds counted already is closed as `kept` too. "Take" is a new edit of the deciding tab: its own client, number and edit id, the stored action, the values the person reviewed as its seen values, and a `take` field that names the copy and the edit. A returned restored edit that meets an unchanged cell is written, also when the record already lists the edit as open from an earlier pass; a later restore then closes the mark as saved. Oracle: it records the origin of every frame from its own generation records and checks that an adopt frame names exactly that origin (G3); that an adopt frame is counted without writing exactly when a person declined it or a cell it was judged against changed (G3 for a wrong `keep`, R8 for a frame written over a value that neither its author saw nor a person reviewed); that the record lists the edit before a frame is kept this way (R11); that the `open` flag is right (G3); that a `returned` answer names a frame of that copy whose cell did change (G3); that the room and the oracle judged the same number of returned frames (G3, in every step check, so an oracle that skips returned frames fails); and that no tab shows its own returned edit as dropped while the record lists it as open (R3). Witnesses: Opus's seeds 325 (profile `v7`, ordered, 29 moves), 284 and 1151 (profile `v6`, scrambled, 33 and 48 moves), shrunk with the planted defect; seeds 78 and 1550 stay as sessions that must pass. Planted defects `returned-frame-not-judged-again`, `returned-frame-loses-its-origin`, `returned-frame-kept-before-its-mark`, `returned-edit-shown-as-dropped` and `oracle-skips-returned-frames`. Scenarios `returned-restore-meets-a-newer-value`, `returned-restore-is-not-shown-as-dropped` and `returned-take-meets-a-newer-value`.

### A delete that removes later values tells someone (condition C2)

105. **A take of a delete, and a delete that returns from a lost room, name the values they remove** (Opus F2, Sonnet F1 and F1b). Story: Ana's row delete is in a recovery copy. Ben changes the cell she saw and fills another cell of the row. Cal's restore shows the delete as a conflict; Cal sees Ben's changed value and takes the delete. The row goes, and the value Ben filled in the other cell goes with it, which neither Ana nor Cal saw. Before, only a delete that a restore applied by itself listed what it removed (rule 87). Now every tab that applies a written delete frame that came from a backup or a take (a restore offer, a take, or either of them returned from a lost room) computes the cells of the row that hold a value its author did not see (`unseenBy`, the same list as rule 87) and shows a `removed` notice with the copy, the delete and the values when the list is not empty (`applyAction` in `tab.mjs`). So the deleter's side and every tab that is in the room are told. The taker's own restore notice lists the values under `removed` (`settleTakes`). Oracle: its expected answer carries the removed list of every such frame, computed from its own reference sheet at the frame's place (`info.removed`, and `takeRemoved` for a take), and a tab that shows another list, or none, fails R9; a restore notice that lists a landed take without its removed values fails R9. Planted defect `taken-delete-hides-removed-values`; the round 4 defect `restored-delete-hides-removed-values` now also covers a restored delete that returns. Scenarios `taken-delete-names-the-values-it-removed` and `returned-delete-names-the-values-it-removed`. **Not changed, on purpose:** a live delete typed in the room, also one that a tab adopts after a room loss, removes the row as before with no removed list (last writer wins, as since round 1; Sonnet F1b names it). A tab that is away when the delete frame is applied and saved learns nothing from a frame; rule 109 is the answer to that, behind its flag.

### The row wait is quiet and has an end (David's decision on form 16)

106. **An edit that waits for its row waits quietly, and only while a room that could bring the row back is open** (changes rule 98). David: "If Tom's work didn't sync, it didn't sync", and no person holds others back. The value waits only while a room that could bring the row back is open. At the next save after that room closes, it stops waiting and stays in the recovery copy like any other unsynced work. In the lab a room is one generation, and the insert of the missing row was seen in a room that was lost. The room that could bring the row back is the one that follows it: a tab that holds the lost room's frames returns there, and its frames are adopted. So a restore waits for a row only while the target file is of the lost room's generation or of the one right after it (`inReach` in `recover.mjs`: the file's epoch is at most one more than the epoch of the generation in which the copy's author saw the insert). In any later file the wait is over: the restore answers that the edit does not fit, as before rule 98, its mark closes as `misfit`, and the edit stays in the copy for inspect and export. If the row comes back after that, it comes back empty, and no restore writes the value by itself. Round 5 read this the short way: any next generation ended the wait, also one that a tab starts to shrink the ledger. Rule 124 (round 6) replaces that test and measures the wait in rooms. No card and no notice: the restore notice lists a waiting edit with the edits that stay in the copy (`left`), not as held; the open mark carries no row (the decision record has three fields again: copy, edit, kind); no tab shows a `waiting` notice, and a `passed` notice carries no row. There is no "add it as a new row" action. Oracle: it decides the wait from its own records with the same reach test (`insertPending`), so a refusal inside the reach fails R10, a wait outside it fails R10, a notice or a mark that shows a wait fails R9, and the end check accepts an edit that was refused after its wait ended though its row is in the final file (`stopped`). Planted defects `edit-waits-for-its-row-forever` and `waiting-edit-shown`; `waiting-edit-not-told` is retired. Scenarios `restored-edit-waits-for-its-row` (the quiet wait, then the row comes back in time and the value lands), `waiting-edit-stops-waiting-after-the-next-room` (the end of the wait) and `waiting-edit-becomes-late-when-its-authors-later-edit-lands`.

### The record of removed values (behind one flag, off; David decides)

109. **With the flag on, the host keeps a record of removed values, and every tab reads it** (Opus F1; `newWorld({ removals: true })`, `--removals` in the fuzzer; off by default, and with it off no code path of this rule runs). Story: Ben fills a cell and closes his laptop. Cal restores Ana's delete of that row, and Ben's value goes with it. Ben's tab was not in the room, so no frame tells it, and when he opens the sheet again the row is gone with no word. With the flag on, a tab that applies a delete from a backup or a take with a removed list that is not empty (rule 105) owes the host one entry: the copy, the delete, its place in the room's history and the removed values. It writes the entry only when a file of the delete's own generation holds the delete's place, which it learns from a receipt or from a file read (`recordRemovals` in `tab.mjs`), and has the write confirmed as for a decision mark. It drops the entry when it reads a file of another generation. That file's history cannot prove the save: the history of a lost room also grows when its frames are brought in again, and there the delete is judged again (rule 104) and applied at a new place, with a new list and a new entry, or not at all. The host keeps one entry per delete and place (`removals`, beside `decisions`; write faults as for marks). Every tab reads the record on each file read and shows a `removed` notice for each entry it has not shown (`readRemovals`), so a tab that was away, or that opens later, is told. The lab shows every entry to every tab; a product would show a person the entries that name a value that person typed. A tab with an entry to write, or with entries it has not read, is not idle. Oracle (class R12): an entry must name a delete at a place where the oracle's own reference removed exactly those values, and an accepted file of that generation must hold that place; at the end, the record must list every such delete of the final generation when a tab that applied it is still open; and every open tab, a fresh one too, must show every entry. **What it does not cover:** no entry is written when no tab that applied the delete sees a file of the delete's own generation that holds it: every such tab closed first, or the generation ended (a lost room, a turn of the ledger) before one of them read the save. The tally `removalMissed` counts the deletes that a file of their generation held and the record does not list. A build can close this gap by sending the entries with the save that first holds the delete, because the saving tab has applied every frame it saves; round 5 did not model that. Rule 125 (round 6) does, and it replaces the separate write, the receipt test and the end condition of this rule. Planted defects `record-misses-removed-values`, `record-entry-not-shown`, `record-written-before-its-save` and `record-trusts-a-later-file` (witness: seed 33045570, profile `v8`, scrambled, 22 moves, from pre-gate `r5p`, where the first build of this rule read a later file's history as proof). Scenario `record-of-removed-values-tells-a-tab-that-was-away`. A row of `regressions.json` can now carry `removals: true`.

### Nobody waits for an absent tab (the leader's check)

110. **A live edit and a save wait for no other tab** (no model change; the check and its tallies are new). David: when four people work together, one person who is away or slow must not hold the other three back. The rules already had this shape, and this round checks it. A request is admitted on the room's own state (ledger count, space, rows); no rule asks for an answer from another tab. A save is a conditional write by any tab of what that tab has applied; no rule asks for another tab's receipt. The frames of a lost room can be offered by any tab that holds them, and every holder offers them from the same place, so a holder that is away blocks nobody (rule 104's `returned` answer is given to each holder that offers, and each can write the mark). The room keeps no frame for a tab that lags: after a receipt it trims its tail, and a tab that fell behind reads the file again. A ledger that is full is trimmed by age when the generation turns, and a tab that was away too long is retired: it goes on under a new client id, and the edits whose fate it cannot know go into a recovery copy (the restorable version David asks for). When the room needs space for a frame that is next in order, it sheds staged parts and parked requests that are not, so a half-sent frame of a slow tab holds no place that another tab's next frame needs beyond its own bytes. The waits that exist are waits of stored edits inside a restore, never of live edits: an edit behind an earlier edit of the same copy on the same cell (rules 56 and 57), an edit that a restore passes over for a person's decision (rules 79 to 84), and the row wait, which now ends (rule 106). The check: the generator's `lull` move settles the connected tabs while the other tabs stay away, and fails with I8 unless every connected tab has all its requests answered, its held frames adopted or stored, its restore job finished and its marks written, and the file holds the room's last frame. The tallies `lulls`, `lullsAway` (a tab was away) and `lullsOwing` (a tab that was away held unsaved frames, open requests, unwritten marks or an unfinished restore) count these checks in every sweep. The check can fail: planted defect `save-waits-for-every-tab` (a tab does not save while another open tab is away) fails it in about half of all sessions, and `returned-frame-waits-for-its-first-holder` (the room gives rule 104's `returned` answer to the first holder only) fails it in its scenario. Scenarios `one-absent-tab-holds-nobody-back` (David's story: three people type on and save while the fourth is away, and the value he sent is saved by their tabs) and `returned-frame-does-not-wait-for-an-absent-holder`.

### What fresh seeds found (gate `r5a` and the soaks after it)

111. **An edit that the record lists as open is never closed by its place in a lost room** (model fix; rule 97 on the replay). Story: Dana restores Sam's copy, the room writes his value and is lost before a save. Tom types a newer value into the cell. The lost room's frames return, the room keeps Tom's value, counts Sam's edit without writing it and marks it open (rule 104). The next file's history now covers the place that Sam's restored edit had in the lost room. Ann's tab also held the lost room's frames and gave them up to a copy, which lists Sam's edit by that place. Before, a restore of Ann's copy read the covered place as "saved": it reported Sam's edit as saved and changed the record from open to saved. The conflict was closed with no person deciding, no file had ever held Sam's value, and Sam's own tab then showed the edit as saved. The same held, since round 4, for a stored edit that a restore passed over and whose lost-room frame the next room skipped as counted (the story of rule 97). Now a replay judges an edit that the record lists as open by its value, whether the ledger counts it or a place covers it (`weigh` in `recover.mjs`): its value in the sheet closes it as saved, and otherwise it shows as a conflict, a misfit or a held edit, or takes the person's decision, as in rule 85. The oracle fails a replay that reports an open edit as covered by a file position (class R11), and its check R3 accepts a place-covered edit that the file's history does not hold only when the record lists it as closed. ### Generators

- **Steered tails** (`--tails ret` and `--tails wait` in `fuzz.mjs`, `tailSession` in `gen.mjs`): a session is the moves of one regression row followed by about 100 random moves. The `ret` weights are Sonnet's (`x/xrun.mjs`): returned frames, strands, decisions and crossings. The `wait` weights start with `solo` and `lull` and favor room losses, ledger turns and restores. Both end a room now and then (`end-room`), which reaches the room's own save. `--row N` pins the row, `--flip` runs the row in the other delivery mode, `--faults` and `--removals` override the row's options.
- **A planted defect is caught through the tail:** with a defect planted, the row's moves are cut to the longest part that still passes, so a catch needs moves of the tail. The report counts the cut sessions and, for each defect, the catches on rows whose whole moves pass.
- **Tails after a shortened row** (`--short`): the row's moves are cut by a number of moves that the seed picks, up to half of them, before the tail starts. Clean sweeps never ran those sessions; planted sweeps did, and a session that failed for another reason counted as a catch.
- **A planted sweep runs every failing session again with the defect off** (`failsAlone` in `fuzz.mjs`) and reports the sessions that fail alone. The gate wants none.
- The move `solo` is new: one tab stays connected and every other tab goes offline.
- A regression row can carry `end`, the seed of the settle at the end of the session, so a failure found through a tail replays as a plain move list.
- New tallies: `rowWaits`, `rowWaitsTurned` (the room had turned its ledger), `rowWaitsEarlier` (the insert was seen in the room before), `removalSaves`, `removalHeld`. `removalWrites` and `removalFaults` are gone with the separate write.
- Profiles `v1` to `v8` are unchanged.

    - **The same rule when a room skipped the take** (model fix, found by the soak of gate attempt `r6bg1`). Story: Tia's take of a row delete was written by a room that was lost. A coworker restored her backup of it, the delete was saved and the row is gone. Her tab was still storing a backup that names the take, so it had not read the save (rule 123). When it gave up the frames of a lost room that had skipped the take as already counted, it showed the take as dropped with a refused notice, as that path does for every kind of edit, and Tia read that her take was refused. A tab that gives up such frames now asks whether the row is gone, for a take of a row delete (`settleOwn` and `tookItsRow` in `tab.mjs`): the take shows as saved. The path is unchanged for every other edit: it still shows dropped with a notice that holds the action. Witness: regression row 210 (soak piece `pk5`, ret tail seed 1120119024 after a shortened prefix of row 181, P6; 2 of 100,000 pinned short tails on that row). Planted defect `skipped-take-of-a-delete-shown-as-refused`.
    - **A version restore can bring a refused take back** (oracle allowance, found with row 210 as a tail prefix). Tia's take was in a version that a version restore replaced, and the row was back in the sheet. Her tab came back, saw the row and showed the take as dropped, which was right. A later version restore brought back a version that holds the take, so the row is gone again. A tab does not change a label when a person restores a version, so the check skips a take that its tab showed as refused before a version restore brought it back (`broughtBack` in `oracle.mjs`). Witness: regression row 211 (local ret tail seed 1000600175 on row 210; 5 of 10,000 tails on that row before the allowance). It carries no planted defect, because the change removes a false alarm.

### The end check and a take that a save holds (condition 3)

133. **The end check accepts saved for an edit that a room refused when an accepted file holds a person's take of it as written** (oracle only; the model was right; the family of rules 66 and 122). Tia's value came back from a lost room to a changed cell and stayed in a backup for a person's decision. A coworker took it, the take was written and a save holds it, so the cell holds Tia's value and her tab shows her edit as saved. The end check had this exemption for an edit that a room refused last and for an edit in the final file's history. It did not have it for an edit that an older room had counted without writing and that the final file's history does not hold. Sonnet's one-line change accepted a take in the final file's history. With the two witness rows as tail prefixes, 26 of 6,000 local tails still failed: a version restore had replaced the version that held the take, which is the accepted case of row 189. So the exemption asks for a take that an accepted file holds as written (`writtenInFile` in `oracle.mjs`). Witnesses: regression rows 195 and 196 (Sonnet's wait tails 903188078 and 930180476 after a shortened row 190, P6).

### A tab's word that the record lists an edit (condition 4)

134. **A tab says that the decision record lists a stored edit only when the record lists that edit** (oracle check at the offer, class R11; the tab's side of rule 129). The room of rule 129 sends an offer back for a mark unless the offer says that the record lists the edit. The oracle checked that word for `open` and not for `listed`. Opus's planted defect `opus-listed-by-copy` sets `listed` when the record holds a mark for any edit of the same backup. With the defect planted, 2,286 of 6,000 local ret tails fail. Witness: regression row 198. Planted defect `edit-listed-by-another-mark-of-its-copy`.

## 18. The split into core, codec and harness (step L1 of the build plan)

The files now sit in three folders, so that the product can take the protocol code from `core/` later. No rule, check, planted defect, generator profile or seed changed. The same gate, run from the tree before the split and from the tree after it on the same seeds, gave equal counts.

- `core/`: the protocol. `ledger.mjs`, `room.mjs`, `tab.mjs`, `record.mjs`, `frames.mjs`, `limits.mjs`, `conflict.mjs`, `recover.mjs`, `fileonly.mjs`, `planted.mjs`, `codec.mjs` and `lib.mjs`. A file in `core/` imports only files in `core/`. A test in `test/lab.test.mjs` fails if one does not, and the same test feeds the check a planted bad import to prove that it can fail.
- `codec-tiny/reducer.mjs`: the reducer that applies one action to the lab's small workbook (`act`). Core never imports it. Core calls `act` in `core/codec.mjs`, and `harness/host.mjs` puts this reducer there with `useCodec`.
- `harness/`: the simulated world and host, the oracle and its reader, the generators, fuzzers, scenarios, replay, shrink and measurements, and `shared/`, `union/`, `vendor/` and `regressions.json`.

Core functions take an `env` where they took the world. They read five things from it, and the test above fails on any other:

- `env.limits`: the lab's caps.
- `env.removals`: whether the record of removed values is on (rule 109).
- `env.split`: whether a nudge only wakes a tab, so that its sync is a move of its own (a generator setting).
- `env.port`: the host and the network. It reads the file, its ETag, recovery copies, decision marks and removed-value entries, and stores the last three. It sends a request and takes an answer, holds the current room, lists the tabs, picks a frame in scrambled delivery, and counts ids (commits, generations, copies, room instances). `hostPort` in `harness/world.mjs` and `filePort` in `harness/fileworld.mjs` build it from the simulated world.
- `env.observer`: the oracle. Core calls the same hooks as before (`onAdmit`, `onWire`, `onAccept` and the rest), with the same arguments. Two counters that core kept on the world are now hooks too: `onReturnCount` (the room's count of returned frames, `world.returned`, checked by rule G3) and `onRefused` (the refused saves of file-only mode, `world.refused`).

Functions that moved, by the file they were in:

- `reducer.mjs`: `act` is in `codec-tiny/reducer.mjs`. `W`, `ledgerMarks`, `newState`, `epochOf`, `resolved`, `covered`, `applyFrame`, `trimLedger` and `nextGeneration` are in `core/ledger.mjs`.
- `tab.mjs`: `hostTake` and `answer`, the simulated host taking a request and answering it, are in `harness/world.mjs`.
- `host.mjs`: `CLOSING` is in `core/recover.mjs`.
- `fileonly.mjs`: the tab side (`view`, `edit`, `settle`, `store`, `keepCopy`, `rekey`, `absorb`, `refresh`, `push`, `save`, `refused`, `deliver`, `nextCommit`, `nextGen`) stays in `core/fileonly.mjs`. ## 19. Round L2a: room frames travel over a lossy wire, and large actions travel in parts on it

Until this round a tab handed a frame to the room and got the room's answer in the same move (`toRoom` in `core/tab.mjs`). So the lab never saw a frame lost on its way, a frame delivered twice, a frame that arrives late, or an answer that never comes back. Rule 13 already said that a paste over one frame's operations travels as parts that commit together or not at all, but every part arrived, once. The product sends frames as HTTP requests, which can fail in all four ways. Rules 135 to 140 were written before the code. The review of the round (one Opus seat; Carbon and Astra were out) found two protocol gaps and the round's own weak spots, and rules 138, 139 and 141 and the M5 check came from it.

135. **A room frame can be lost, duplicated, delayed or unanswered.** A tab may put a frame on the wire (`post`) instead of handing it over. The wire holds frames in transit. A frame on the wire lands at whatever room the host has when it arrives, or at none, and its answer may be lost. The network may drop a frame before it lands, or deliver a copy of it. Every earlier rule of the room judges a landed frame the same way as before: the generation fence, the request ledger, the adopt gap rule, the copy offer memory, and the part stage.
136. **A tab acts only on the answer to a frame it still waits for.** It keeps the frames it put on the wire until their answers come. An answer to a frame it no longer waits for, such as the second copy of a duplicated frame or the late answer to a frame it already sent again, changes nothing in the tab. No plant: no scenario was found in which acting on such an answer changes an outcome once rule 138 holds, so the rule is kept as the product's behavior without a witness.
137. **A tab whose wait for answers runs out sends again.** It forgets the frames it waits for and sends again, from its own state, every request it has not seen admitted, every held generation it offers, its open restore offer, and every receipt whose answer it never got (rule 139). This is the resend it already makes after a refusal for space and after it reconnects (`resend`). Sending again is safe because every frame kind is idempotent at the room: a request at or below the client's ledger count is a duplicate, an adopt item at or below the lineage count is skipped, a copy offer gets the answer the room gave it (rule 138), a receipt at or below the room's base is `old`, and a part fills its stage only once per index. A paste sent again after a lost part completes the stage the earlier parts left. Witness: scenarios `lost-part-is-sent-again` and `duplicated-request-counts-once` (a write delivered twice with both answers lost, then sent a third time when the wait runs out); plants `wire-never-resent` (the tab forgets the frames and sends nothing, also caught by the `v9` fuzz as a stall) and `no-dedup`.
138. **The room answers a restore offer it has judged with the same answer every time.** Before this round the room kept its answer only for an offer that wrote nothing. An offer it admitted was judged again when it came back, and the second answer was "already counted". Story (found by the review): Cal restores Ana's recovery copy on a slow connection; the room writes the value, but the answer arrives after Cal's wait ran out and his tab sent the offer again; the notice then says the edit was already saved, or counted and not in the sheet, instead of restored, and Cal cannot tell what the restore did. Now the room keeps every answer it gave, keyed by job, entry and decision, for as long as it keeps the job. Profiles `v1` to `v8` are unchanged by it (see Generators). Witness: scenario `restore-offer-answered-late`; plant `wire-offer-judged-again`, which fails with R9 there and in 2 of 600 `v9` sessions. Two recorded witnesses caught their plant only through a second judgment of an offer the room had already admitted, so on their moves the plant now changes nothing; as in fix round 4 (rule 94), each stays with a plant of the same harm it still catches: `witness-moves-5-ordered` moves from `room-restore-trusts-the-tab` to `restore-skips-ledger`, and `witness-moves-19715-ordered` from `restore-answer-of-another-job` to `restore-notice-before-save`. Both retired plants are still caught by other scenarios (`room-restore-applies-and-saves` and the restore scenarios for the first, `witness-moves-39644-ordered` for the second).
139. **A receipt whose answer was lost is sent again.** A tab makes a receipt only when it learns of a save, so a lost receipt was never made a second time. Story (found by the review): Ben types a value and Ana's tab saves the file; Ana's receipt is lost; Ben's tab shows his edit as not saved until someone saves again, and the room counts the rows as unsaved, so it never ends when empty (rule 17). Witness: scenario `lost-receipt-is-sent-again`; plant `wire-receipt-not-resent`. Only the scenario catches it: the next save, a refused save or a re-attach makes a new receipt, so a random session almost never ends with the room unaware of a save (0 of 600 locally).
140. **The parts of one action commit together, wherever other frames land between them.** The room admits the action when its last part lands, at that point in the one order. A peer's write that lands between two parts is ordered before the paste. A room loss between parts loses the stage with the room; the author's request is still pending, and the tab sends it whole to the next room when it joins. Witnesses: scenarios `peer-edit-lands-between-parts` and `room-lost-between-parts`, whose own checks test the order and the single admission. The plant listed for them, `paste-part-admit`, fails as soon as the first part lands, before the peer's write or the room loss, so no plant shows that the "between parts" checks themselves can fail; the checks are direct assertions on the room's log.
141. **The room refuses a part from a connection that has ended, and stages it nowhere.** The room dropped that connection's stage when the connection ended (rule 14), and it now remembers the ended connection until the same tab connects again. Staging a late part again would hold up to one action's bytes, 3 MiB of the room's 6 MiB, until the room ends, because a stage that is next in its client's order is never shed. Story: Ana's laptop loses Wi-Fi in the middle of a large paste and she closes the tab; two of its parts land a moment later; without the rule, everyone in the room has half the space for the rest of the session. The rule lives in the room (`admitPart`, `dropConnection`, `rejoin` in `core/room.mjs`), not in the simulated network, because the product takes the room from `core/` (the review found the first form of this round had it in `harness/world.mjs`). A part sent before a connection drop that lands after the tab reconnected is staged, and the tab's resend completes it. Witness: scenario `late-part-after-the-tab-closed`; plant `wire-late-part-staged`, also caught by the `v9` fuzz through M5 (2 of 600 locally).

### Oracle

- **M5 (new): at the end of a session the room holds no stage of a closed tab.** Without it a product room that leaked stages would pass every session of the gate (the review). It fires in no clean session of `v1` to `v9`.

### Generators

Profile `v9` is new: `v8`'s table (with its restore, decision, `strand`, `cross` and `come-back` moves) with `out` replaced by `post`, pastes twice as frequent, and five new moves: `land` (a frame on the wire lands and its answer arrives), `land-lost` (it lands and its answer is lost), `drop` (it is lost before it lands), `echo` (the network delivers a copy), and `wait-out` (a tab's wait for its answers runs out). The first form of `v9` was built on `v3` and never put a restore offer on the wire, which is how rule 138's gap stayed hidden; the review caught it. `checkpoint` still hands frames over in one move, so a session mixes both paths. The end of a session lands every frame on the wire and runs out every wait that has no frame left on the wire. Profiles `v1` to `v8` are unchanged: 60 seeds per mode of each of `v1` to `v8` give byte-identical sessions (moves, accepted saves, sequence, ETag, end verdict) on the tree before this round and after it, with rule 138 and M5 in.

What `v9` reaches, measured by the review on its first form over 300 sessions: frames that land after their tab moved to a new generation (2,257), at a room of another generation (2,765), answers ignored after a resend (3,648), late parts refused (968), receipts dropped (22). Never reached even with the restore moves: the `retired` and `returned` answers over the wire.

### What the gate adds

`run-final.sh gate` adds `profile-v9-ordered` and `profile-v9-scrambled` (each `SIDE_SEEDS`, 20,000 by default, at 400 moves) and `mutants-v9`, the mutant sweep of `wire-never-resent`, `wire-late-part-staged` and `wire-offer-judged-again` under `v9`. `wire-receipt-not-resent` is caught by its scenario only. All four plants are named `wire-` so that the default `v3` mutant sweep, which cannot reach the wire, leaves them out. Before the box: 1,000 sessions of the final `v9` (500 per mode) locally, no failure.

### Not changed, on purpose

- The split of an action into parts stays in `core/frames.mjs`, and core still reads paste cells in about twenty places (`cellsOf`, `rowsOf`). Moving only `split` and `assemble` behind the codec would not make core codec-neutral. The whole action surface moves behind the codec contract at once in the product's step P2, where the codec laws C1 to C10 hold it.
- A large action other than a paste (the undo of a column delete) is not modeled: the small workbook has no columns. Core stages any action the same way, by part index, so the sheet codec's law C6 (`assemble(split(action))` equals the action, every part inside the frame limits) and the adversarial campaign X1 prove it for the real codec.
- A duplicated part that lands after its paste was admitted starts a stage that never completes. It is not refused: it is never next in its client's order, so the room sheds it as soon as it needs the space (rule 14), and it is dropped when the connection ends. No person story.
- A tab's outbox can hold several copies of one frame after repeated resends (older than this round: up to 441 in one `v3` tab). The room makes every copy a no-op. No person story; the product client should still replace rather than append when it resends.
- The rest of plan 09's L2 list (receipts made by the host, the establishing commit made by the host, outside writes with equal tables, a dropped commit tag, a host client's action that waits for a commit, file-only restore with `If-Match` retry, edits that cannot be judged, two open copies, a forgotten job, "Keep current for the rest", a browser save by a client that does not know the room) is round L2b.
